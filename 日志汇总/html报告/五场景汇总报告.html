深度分析：Token 与耗时变化的根本原因

一、耗时变化的原因

耗时减少的核心驱动：API 调用次数大幅减少

每次 API 调用都有固定开销（网络延迟 + 模型思考时间），减少调用次数直接减少耗时。

场景API 变化耗时变化减少原因
S1 日志分析119→26（-78.2%）-73.6%ctx_batch_execute×6 替代 118 次 Bash + 35 次 Grep
S5 项目逆向56→15（-73.2%）-67.5%ctx_batch_execute×4 替代 8 次 Agent 委派
S2 代码优化47→28（-40.4%）-6.0%插件替代部分工具调用

两个关键机制：

  • 批量执行消除往返：不带插件每个 Bash/Read 都是一次独立的工具调用→一次 API 往返；ctx_batch_execute 一次执行多个命令，往返次数从百级降到个位数。
  • 多 Agent 协作被替代（S5 最典型）：不带插件用 8 次 Agent 委派子任务，每次 Agent 都需要「创建子 agent→传递完整上下文→子 agent 执行→返回结果」，开销极大；带插件用 ctx_batch_execute 直接执行，省去了多 Agent 的上下文传递和创建开销。

二、Token 变化的原因

Token 减少的核心驱动：API 次数减少 → 上下文累积减少

每次 API 调用都需要把完整对话历史（含所有工具调用和结果）作为输入，API 次数越少，累积的上下文越少。

三个具体机制：

  • 批量执行减少中间结果累积：S1 不带插件 118 次 Bash，每次 Bash 的输出都进入上下文，累积起来非常大；带插件 6 次 ctx_batch_execute，批量执行的结果经过聚合，进入上下文的内容更少。
  • 多 Agent 上下文被消除（S5）：不带插件 8 次 Agent 委派，每次子 agent 的分析过程和项目文件内容都会返回并累积到主上下文；带插件没有子 agent，上下文更精简。
  • 输出量同步减少：S1 输出 -70.6%，S5 输出 -64.8%，输出 token 也是总 token 的一部分。

三个具体机制：

  • 插件工具格式更冗长：ctx_execute_file、ctx_execute、ctx_search 的调用参数和返回结果比原生 Read/Bash 包含更多元数据（执行环境、搜索范围、结果格式化等）。S4 用 36 次插件工具替代 51 次原生 Read，API 只减了 11.3%，但每次调用的输入量暴增 73.9%。
  • 缓存命中率下降：带插件后上下文结构变化（插件工具的调用格式与原生工具不同），导致缓存无法命中。S4 缓存命中率下降 6.6%，意味着更多 token 需要重新计算而非从缓存读取。
  • 任务管理工具增加上下文（S3）：带插件后 agent 选择了更细粒度的任务拆分（TaskCreate×2, TaskUpdate×4），这些工具的调用和结果增加了上下文冗余。S3 API 反而增加了 15.8%（19→22），更多调用 = 更多上下文累积。

三、核心规律总结

插件效果 = 批量执行带来的 API 减少收益 − 插件工具本身的开销

场景API减少收益插件工具开销净效果
S1 日志分析████████████ 强██ 弱显著正向
S5 项目逆向████████████ 强██ 弱显著正向
S2 代码优化██████ 中████ 中轻微正向
S3 2048游戏██ 弱/反向███ 中中性偏负
S4 书籍分析██ 弱█████████ 强偏负向

核心规律：

  • 当任务有大量可批量处理的重复性操作时（日志分析、项目逆向），API 减少收益远大于插件开销，效果显著正向。
  • 当任务是深度阅读+长文生成或从零生成时，可批量处理的操作少，插件工具开销占比高，甚至增加 API 次数，效果偏负。
  • Token 变化主要跟随 API 次数，但插件工具的冗长格式和缓存命中率下降会在 API 减少不多时导致 token 反而增加。

关于「最长 API 调用」的三条规律

  • 规律一：最长调用本质是「一次生成大量 token」——输出生成阶段（output_ms）占 62%~98%，输出 token 从 3,208 到 13,429 不等。慢不在网络（首字节仅 1.5~2.4 秒），而在模型长文/长代码生成。
  • 规律二：思考只在「复杂推理」任务触发——不带插件时，日志分析（16.3 秒思考）和 2048 游戏设计（37 秒思考）触发深度思考；而代码重构、书籍分析、文档生成几乎零思考（<1 秒）。说明 deepseek-v4-pro 的 thinking 是按需触发的。
  • 规律三：带插件后思考普遍下降——S1 思考占比 34%→1%，S3 22%→6%。因为插件提供了 ctx 批量执行/搜索工具，模型把「探索推理」转交给工具，自身不再深度思考（工具替代思考）。注：带插件的轮次其实更少（批量执行减少了 API 往返，如 S1 119→26、S5 56→15），并非「拆碎更多轮次」。

使用建议（决策结论）

  • 强烈推荐用插件：日志分析、项目逆向、大批量命令执行、多 Agent 协作类任务（实测省 53%~65% token、67%~74% 时间）。
  • 不推荐用插件：从零编码生成（2048 类）、深度长文阅读（书籍分析类）——核心耗时是模型生成，插件工具反而增加 token（+20%~+74%）。
  • 通用规则：任务有大量可批量/可搜索的现有数据 → 用插件；任务以「从零生成长内容」为主 → 不用插件。
  • 验收提醒：无论哪种模式，省了 token 都要核验交付物是否完整达标。

第 2 层：PreToolUse hook 拦截原生工具时注入的「劝导」

  • createReadGuidance（拦截 Read）：想分析文件 → 用 ctx_execute_file，字节留在沙箱
  • createGrepGuidance（拦截 Grep）：想统计/聚合匹配 → 用 ctx_execute 跑搜索
  • createBashGuidance（拦截 Bash）：想处理输出 → 用 ctx_batch_execute / ctx_execute
  • createExternalMcpGuidance（拦截外部 MCP）：大 payload → 用 ctx_execute 过滤，或 ctx_fetch_and_index

第 3 层：6 个沙箱工具 schema（description 超长，随每轮请求发送）

工具核心承诺 / 机制
ctx_execute沙箱跑代码，只返回 console.log 的内容；输出 >5KB 自动索引、只回标题+预览（server.ts:1662,1680）
ctx_execute_file对单个文件跑代码，文件内容经 FILE_CONTENT 变量注入，原始字节不进对话（server.ts:2058）
ctx_search对已索引内容（含会话记忆）做 BM25 检索，多 query 一次调用（server.ts:2554）
ctx_batch_execute并行跑多命令 + 自动索引 + 同轮返回匹配段，免后续搜索（server.ts:3679）
ctx_index把内容存进 FTS5 知识库，原文不回声、按需检索（server.ts:2248）
ctx_fetch_and_index抓 URL → 转 Markdown → 索引，返回小预览窗口（server.ts:3423）

关键机制（server.ts:1504）：ctx_execute / ctx_execute_file 有 source-code echo——模型写的代码会被「回显」（最多 CODE_ECHO_MAX=2000 字符）加在结果前。这是「写脚本比 Read 更贵」的源码级证据。

二-补充：PreToolUse 的触发时机与注入机制

触发时机：模型生成 tool_use（决定调工具）之后、CLI 实际执行工具之前。源码 pretooluse.mjs:164 读的是 input.tool_name（模型这次要调的工具名）——证明 hook 拿到时，模型已经做出了「调哪个工具」的选择。

两类动作：context（劝导）vs deny（拦截）

动作机制生效时机对应场景
context（劝导）返回 hookSpecificOutput.additionalContext（formatters.mjs:79）追加到【下一轮】模型输入，影响下次选择Read/Grep/Bash 劝导
deny（拦截）返回 permissionDecision: "deny"（formatters.mjs:11）当场拒绝当前调用curl/wget、WebFetch

劝导有节流：不是每次调用都注入

routing.mjs:36 注释明说「each advisory type at most once per session」（每类劝导每会话最多一次）。Read/Grep/Bash 用 guidanceOnce（每类每会话最多注入 1 次）；外部 MCP 用 guidancePeriodic（每隔 N 次再提醒一次）。

五、根本原因

S4 是「读一本书 → 写长文」的任务。写长文必须理解书的内容，而理解内容必须让内容进上下文——所以插件的「把原始数据挡在沙箱外」这套，在 S4 里省不掉（内容终究要进来喂给模型）。

但插件不管任务性质，仍然逼模型「别读文件、写脚本去读」，于是模型白写了 30+ 段 JS，额外付出了：routing block 固定税（~2.5K×每轮）+ 写脚本（输出）+ 代码回显（2000 字符/次）+ 沙箱搬移（Bash cp）。该省的一点没省，反而多付了一堆固定成本。

结论：插件省的是「重复命令的往返」，S4 没有可省的往返，只有「写脚本」的纯额外开销 → 新增输入 +73.9%（367,662 → 639,182）。
