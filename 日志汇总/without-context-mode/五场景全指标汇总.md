## 三、关键发现

### 1. S3（2048游戏）最快最轻，但单次调用最长

- 总时长仅 **8分06秒**，19 次 API 调用，是五个场景中最快的
- 但**单次最长 API 调用高达 167.9 秒**（id=9，输出 13,429 token），是五个场景中单次最长的
- 说明 2048 游戏场景整体任务量小，但有一次超长输出生成（可能是完整游戏代码或策略分析）

### 2. S5（项目逆向分析）输出最多，多 Agent 协作

- 输出 tokens 最多：**76,172**，远超其他场景
- 缓存命中率最低：**88.4%**（其他场景 92%~96.2%）
- 本地处理平均时长最短：**0.61s/次**，流程最紧凑
- 大量使用 Agent 工具（8次），是典型的多 agent 协作模式
- API 累计耗时最长：19分06秒，占总时长的 97%

### 3. S1（日志分析）最重，本地处理最多

- 总时长最长：**21分12秒**
- API 调用最多：**119次**（是 S3 的 6.3 倍）
- 缓存读取最多：**592万 token**
- 本地处理总时长最多：**4分17秒**，平均 2.18s/次
- 本地处理中位数间隔 1.64s，有 2 次间隔超过 10 秒，说明日志分析需要大量本地命令执行和数据处理
- 最慢流式输出仅 11.7 tok/s，是所有场景中最慢的单次

### 4. S2（代码优化）缓存效率最高

- 缓存命中率最高：**96.2%**
- 缓存读取/新增输入比最高：**25.3倍**（S1 为 12.8x，S4 为 11.5x）
- 流式输出速度最快：平均 52.7 tok/s，最快 81.0 tok/s
- 本地处理极少：仅 33 秒，平均 0.73s/次
- 代码优化的上下文高度稳定，每次调用只新增极少量内容（工具结果、简短消息），绝大部分命中缓存

### 5. S4（书籍分析）上下文最大

- 平均每次缓存读取最高：**85,995 token**（其他场景 41k~59k）
- 单次缓存读取峰值最高：**155,648 token**
- 工具调用最少：仅 15 次，是纯阅读+长文输出型任务
- R4 轮缓存命中率异常低（51.2%），其他轮 91%~97%，值得排查

### 6. 共性发现

- **所有场景 cache_creation 均为 0**：缓存是自动管理的，没有显式缓存创建操作
- **流式输出速度高度一致**：平均 47.9~52.7 tok/s，最快 73~81 tok/s，模型生成性能稳定
- **都是"读多写少"型**：输出仅占实际总输入的 0.9%~3.2%，大量 token 用于上下文读取
- **缓存命中率都很高**：88.4%~96.2%，prompt 缓存机制效果显著，实际计费成本远低于账面 token 量
